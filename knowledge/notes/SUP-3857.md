## Problem

Boden (split from a Boden/KWG ticket). A planner relaunches an item that is
already in markdown by picking new Relaunch, MD and Exit weeks. Relaunch and
Exit keep their new values, but MD Wk reverts to the old, already-passed week.
This showed in Style Edit after replan and in Assortment by Floorset right
after the popup's ✓. The relaunched item then plans markdown from the wrong
week. Suhel marked it working in QA on 2026-06-15. On 2026-07-09 Jatin and
Olga reported it still broken in Upgrade (Staging) and asked what had changed
in QA.

## Diagnosis path

- **UI config:** ruled out. Boden's lifecycle viewdefns set up
  Relaunch/MD/Exit editing the same way Express does
  (`boden-configs/uidefn/view/AssortmentStyleEditSectionLifecycle.viewdefn:20-31`).
  The viewdefns are identical on QA and Staging (user diff:
  `AssortmentLinePlanByFloorset.viewdefn`, `AssortmentStyleEditSectionLifecycle.viewdefn`).
  No config commit mentions SUP-3857. The two lifecycle-adjacent commits
  before 2026-06-15 don't touch MD: `f16f915` adds Pre-Season Rating to the
  popup, and `19ecebe` adds two price-band attributes.
- **Frontend and backend:** ruled out. The Floorset popup (`Lifecycle.tsx`)
  and Style Edit both send `erlstmkdnwk` with the new value. darwin's
  `AssortmentController.updateLifecycleParams` treats every field the same
  and never names MD or Relaunch. Boden's only save plugin
  (`plugins/modification/inject_dc.groovy`) just fills in the location.
- **Replan:** ruled out as the cause. The replan copies the Postgres row into
  the plan session, passes `erlstmkdnwk` through unchanged, and appends it to
  the ClickHouse history (`pivot/FlowSheetPlanPivot.pivotdefn:869 → :11705`).
  The git pivot has no Postgres writes. The ticket's own Floorset steps show
  the old MD in the grid before any replan, which points at the save.
- **Where the UI reads MD from:** Postgres, not a pivot. Style Edit uses
  `/api/assortment/style/lifecycleParams` → `AssortmentHelper.fetchLifecycleParams`
  → `AttributeOperation.getAttributesByOwner`. The Floorset grid column
  `attribute:erlstmkdnwk:id` is filled after the pivot by
  `AttributePostProcessor.loadDecorationTable` from pgDataSource. So whatever
  is in the Postgres row is what both screens show.
- **Postgres triggers:** the lead. Evereve's
  `md_trigger_on_update` (`customers/EE/postgres_schema.sql:16647`) has an
  "old MD already passed → undo" branch plus a relaunch-aware branch. A
  QA-vs-"Staging" trigger dump then showed the "Staging" `md_trigger_on_update`
  WHEN still had `old.erlstmkdnwk < old.plan_current`, and
  `exit_trigger_on_update` had `old.exitdate < old.plan_current`. QA had
  removed both. The function `md_trigger_on_update_validity_check()` runs
  `SET erlstmkdnwk = OLD.erlstmkdnwk`, so any item already in MD had its MD
  reverted in the same transaction as the save.
- **Dead end, and the costliest one: a stale "Staging" server.** That dump
  came from `172.16.80.198 / db bd`. Its `plan_current` and `plan_end` in
  `bd_serviceparams` were 2025-W20 and 2026-W32, and the attribute table's
  last write was `max(updated_at) = 2025-06-19 19:12:25`. It was a primary,
  not a replica (`pg_is_in_recovery = f`). The Staging UI offered periods
  from 2026-W40 and ClickHouse was at 2026-W39. That can't happen, because
  darwin builds the UI week range from `bd_serviceparams`
  (`AssortmentHelper.getRange`, `ScopeDataController.getDateContext`). So the
  app was not using that database. The same mismatch made grid items look
  "in ClickHouse but not in Postgres". The user moved to the correct Staging
  server, called **Bonus** (plan_current 2026-W40).
- **Correct Staging (Bonus):** matches QA. The table DDL (including
  `ticketprice_locked`), all 10 triggers, and all 5 trigger functions
  (`md_/exit_/dbt_after_md_…_validity_check`, `store_eligibility_trigger`,
  `update_week_indxes`) are identical to QA. The lock is **not** in Staging
  today.
- **Root cause:** a Postgres trigger lock. Older `md_trigger_on_update` and
  `exit_trigger_on_update` have a WHEN clause
  (`old.<col> < old.plan_current`) that undoes any MD or Exit change once the
  old week has passed. It ignores `relaunchweek`, so relaunch edits are
  silently reverted. QA removed the clause directly in the DB. The trigger
  DDL is not in any repo, so the change had to be applied to each
  environment by hand. Bonus has it today, and the old server still shows the
  locked version.

## Fix

No code or config change. The fix is Postgres trigger DDL, and QA and Bonus
already have it:

```sql
CREATE OR REPLACE TRIGGER md_trigger_on_update
    AFTER UPDATE OF erlstmkdnwk ON public.bd_ma_stylecolorchannelattributes
    FOR EACH ROW
    WHEN ((new.erlstmkdnwk <= new.dbt_wk OR new.exitdate <= new.erlstmkdnwk) AND pg_trigger_depth() = 0)
    EXECUTE FUNCTION public.md_trigger_on_update_validity_check();

CREATE OR REPLACE TRIGGER exit_trigger_on_update
    AFTER UPDATE OF exitdate ON public.bd_ma_stylecolorchannelattributes
    FOR EACH ROW
    WHEN (new.exitdate <= new.erlstmkdnwk AND pg_trigger_depth() = 0)
    EXECUTE FUNCTION public.exit_trigger_on_update_validity_check();
```

If Prod still has the lock, apply the two statements above through the
normal DB change process, after saving Prod's current definitions for
rollback. Leave the other QA-only differences out of this ticket: the
ticket-price lock (`ticketprice_locked`, `update_ticket_prices`,
`trigger_update_price`). The old/new diff and the Prod
check/fix/rollback script are in `tickets/SUP-3857/trigger-snapshots.sql`.
The current QA = Bonus DDL is in
`customers/BOD/db/bd_ma_stylecolorchannelattributes.sql`, and the trigger map
is in `customers/BOD/db/README.md`.

## Knowledge gained (techno-functional)

**Technical:** Boden's lifecycle rules are Postgres triggers on
`bd_ma_stylecolorchannelattributes`, and none of them are in git. An
`AFTER UPDATE OF <col>` trigger with a `WHEN` guard calls a
`*_validity_check()` function that resets the column to `OLD`, inside the
same save transaction. The API still returns success, and `pg_trigger_depth()
= 0` stops it recursing. The UI's lifecycle weeks (Style Edit REST call, and
the Floorset `attribute:` columns) and the UI's current week and range
(`bd_serviceparams`) are read from **Postgres**. ClickHouse
`bd_ma_stylecolorchannelattributes` is only an append-only history, and the
item lists come from ClickHouse pivots. So a "reverts after replan" symptom
usually means the Postgres row was already reverted at save time.

**Functional:** once an item is in markdown (MD Wk before the current plan
week), its MD week is history and is normally locked. The UI week picker
greys out passed weeks, and the old trigger enforced the same lock in the
DB. A **relaunch** starts a new lifecycle, so a new, future MD week is
legitimate even when the old one has passed. The old lock didn't account for
that. QA's fix removed the lock completely. As a side effect, MD and Exit
can now be moved for any in-MD item, not only relaunched ones. This was
accepted on 2026-06-15, but it's a product decision, so confirm it with the
reporter before promoting to Prod.

## Gotchas

- **Confirm you're on the app's live DB before trusting a dump.** In Boden
  Staging, `172.16.80.198 / bd` is an old copy the app doesn't use. Check
  `bd_serviceparams.plan_current` and `max(updated_at)` on the attribute
  table against the UI's current week. If they disagree, you're on the
  wrong server. The live Staging DB is called **Bonus**. Staging, Upgrade
  and Bonus all mean the same environment.
- **Pick test items per environment.** "In MD" means
  `erlstmkdnwk < plan_current AND exitdate >= plan_current`, using the row's
  own `plan_current`. An item in MD in QA may not be in MD in Staging.
  Testing on a not-in-MD item always "passes" and proves nothing. Query in
  `tickets/SUP-3857/diagnostic-queries.sql`.
- **Style Edit lists styles, not style-colours.** Its list comes from
  ClickHouse `bd_temp_flow_status_prep` (via `AssortmentFitStyleZeros.pivotdefn:284-330`),
  which the replan writes. An item only appears once it has been replanned
  and has rows in the scope's weeks and location.
- **Only Exit is editable on an in-MD item's Debut/MD/Exit row.** That's
  expected, because `WeekRangePicker.tsx` disables passed weeks. Use the
  **Relaunch** row instead. A Relaunch week after the old MD unlocks MD
  (`calculateNextOptionsState`, `disableOverlap`).
- **The popup's "checkmark"** is the green ✓ at the bottom right of the
  Style Color Parameters popup, which saves. The ✓ inside the week calendar
  only fills in the fields.
- **Test items can't be restored through the UI.** Their original MD
  (2026-W39) is now in the past. Restoring them needs a SQL update, and
  only if the reporter asks.
- **Separate issue, not this ticket:** Wks at FP and Initial Intake Wk are
  counted from Debut, not Relaunch. This applies to the popup
  (`AssortmentLinePlanLifecycleTab.viewdefn:43,:70`) and to the
  `update_week_indxes()` recompute. B2962AQU shows 27 Wks at FP
  (W22→W49) where relaunch-based counting would give 2. Express behaves the
  same way. It's a candidate for its own ticket.
- **Don't copy QA DB objects wholesale.** `update_week_indxes()` writes
  `ticketprice_locked`, so any environment without that column would fail
  every lifecycle save. git main's `FlowSheetPlanPivot.pivotdefn:106` also
  selects it.
