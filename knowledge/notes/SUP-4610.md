## Problem

AEO Hindsighting. Two screens have a **Level** dropdown (Department, Super
Class, ERP Class; Top Down adds Brand Group, Brand, Division, Sub Division) in
their left-hand Companion View: **Category Recap > Cat Summary** (Bottom Up and
Top Down) and **Size Views > SKU View** (Bottom Up only). At those levels one
card stands for a whole group, so the pivot has to pick one style color whose
photo represents it. For the same scope (012 - MENS PANTS, North America,
2026-W28) and Level = Department, Cat Summary showed `0125_4711_238` (#3 by
Net Sls $ and units in Grid View) while SKU View showed `1522_5434_044` (#1 by
both). The client asked for, at minimum, one consistent rule on both screens,
and ideally the **#1 style color by Net Sls $** (`net_sls_r`).

## Diagnosis path

- **Image wiring (same on both screens):** the Worklist view maps
  `"image": "attribute:img:name"`
  (`uidefn/view/HistoryCatRecapCatSummaryWorklist.viewdefn:33`,
  `TD_HistoryCatRecapCatSummaryWorklist.viewdefn:33`,
  `HistorySKUWorklistView.viewdefn:42`). The models
  (`uidefn/model/HistoryGrid_Companion.modeldefn`,
  `uidefn/model/HistorySkuCompanion.modeldefn`) declare
  `additionalDecorations: [{level: stylecolor, columnName: top_stylecolor}]`.
  darwin's `pivot/processor/AdditionalLevelPostProcessor.java` copies
  `top_stylecolor` into the `stylecolor` level, and the `img` attribute exists
  only at stylecolor level (`conf/M_Meta.conf:154`, `:390`). So **the image is
  whatever style color the pivot returns in `top_stylecolor`**.
- **Routing:** `uidefn/conf/AssortmentUiConf.confdefn:750-769` (Cat Summary →
  model `HistoryGrid_Companion`, `bottom-up` + `top-down`) and `:1417-1435`
  (SKU View → model `HistorySkuCompanion` → pivot `HistoryGridSKU_Companion`,
  `bottom-up` only).
- **The pick (pre-fix):** both pivots built a per-session `TOP_PRODUCT` table
  and chose `ORDER BY <level>, ttl_net_sls_u desc LIMIT 1 BY <level>`. So both
  ranked by **units**, not dollars. `ttl_net_sls_u = sum(net_sls_u)` from
  `aeo_sku_temp_flow_flag`, but at different grains:
  - Cat Summary: `pivot/include/history_product_ty.ftl` (`PRODUCT` table)
    groups by **stylecolor**.
  - SKU View: `pivot/include/history_product_ty_sku.ftl` (`TY_PRODUCT` table)
    groups by **product = SKU**.
- **Ruled out: "SKU View favours items with few sizes because units are
  concentrated per SKU".** AEO QA ClickHouse showed `aeo_sku_temp_flow_flag`
  does **not** split units by size. For 2026_W21 every SKU of
  `CO0123_4882_064` (cargo) carried 695 and every SKU of `CO1229_5168_064`
  (jogger) carried 327. Those are the same as each style color's weekly total
  in `aeo_p_history_agg`. The table repeats the style color's `net_sls_u` on
  every SKU row.
- **Consequence (confirmed by query, scope 2025_W34–2026_W21):**
  - Cat Summary sums the repeated rows, so its score is **units × size
    count**. The cargo had 81,360 units × 49 SKUs = 3,986,640 and ranked #1.
    The jogger had 144,254 units × 13 SKUs = 1,875,302 and ranked #5, even
    though it sold about 77% more units.
  - SKU View takes the single top SKU row, which equals the style color's real
    units (jogger SKUs at 144,254), so it picked the real #1 by units.
- **Ruled out: location scope.** `sku_temp_flow_flag` is never filtered by
  location in these pivots, but North America is the only AEO location, so it
  makes no difference here.
- **Ruled out: Bottom Up vs Top Down.** Both use the same model and pivot. The
  TD viewdefn differs only in the extra Level options.
- **Ruled out: Order By dropdown.** It only re-sorts the companion list. The
  pivot ranks independently of it.
- **Label check:** "Net Sls Rtl" (companion Order By,
  `uidefn/view/HistoryCompanionListSort.viewdefn:9-10`) and "Net Sls $"
  (`HistoryRollUp.viewdefn:13-16`, Cat Summary Key Financials) both use
  `dataIndex: net_sls_r`. They are the same measure.
- **Root cause:** both pivots picked the image by Net Sls U read from
  `sku_temp_flow_flag`, a table that repeats the style color's units on every
  SKU row. Cat Summary summed those rows, which inflated items with many sizes.
  SKU View took one row. The two screens therefore used two different rules,
  and neither matched the requested Net Sls $ rule.

## Fix

`s5-stratos/aeo-configs`, branch **`SUP-4610`** (cut from `hindsighting`),
commit `1a2ce34` (2026-10-08), 2 files, +40/−10:

- `pivot/HistoryGrid_Companion.pivotdefn` (Cat Summary, BU + TD) and
  `pivot/HistoryGridSKU_Companion.pivotdefn` (SKU View, BU):
  - `TOP_PRODUCT` gets a new column `rank_net_sls_r =
    ifNull(sc_net_sls_r, 0)`, attached by a new `ANY LEFT JOIN` subquery on
    `aeo_p_history_agg`: `sum(net_sls_r * exchange_rate)` grouped by
    style color. It uses the same filters as the grid and the card's own
    Net Sls $: `time IN ty_week_id`, `prodlife IN (${LEAF_PRODLIFE})`,
    `location IN LOCATION`, `cluster IN (${LEAF_CLUSTER})`. The exchange
    rate comes via `INV_LOCATION` (store → marketplace) → `currency_conv`
    (week + marketplace).
  - The existing hierarchy join switched from `USING (product)` to
    `ON p.product = h.product`. This ClickHouse version rejects a second
    `JOIN ... USING` at the same FROM level ("Multiple CROSS/COMMA JOIN do not
    support USING"; see the existing comment in
    `HistoryGridSKU_Companion.pivotdefn`).
  - SKU pivot only: `PRODUCT.product` is the SKU there, so the dollar
    subquery filters and joins on `PRODUCT.stylecolor`
    (`p.stylecolor = y.sc_stylecolor`) and selects `p.stylecolor` explicitly.
  - Image pick changed to `ORDER BY <level>, rank_net_sls_r desc, stylecolor
    LIMIT 1 BY <level>`, so the winner is the #1 Net Sls $ style color and a tie
    always goes to the lowest style color id.
- **Unchanged on purpose:** the card metrics (`COMPANION_METRICS`),
  `SCCOUNT_PRODUCT`, SKU View `agg_shp_u` (still `sum(ttl_net_sls_u)`), the
  shared includes `history_product_ty*.ftl` (used by other pivots), and the
  pivot output columns. `ANY LEFT JOIN` keeps the `TOP_PRODUCT` row set
  identical.
- **Blast radius:** a repo-wide search found `TOP_PRODUCT` only in these two
  pivots, and it is a `${SESSION_ID}` table, private to each request. Two other
  models point at these pivots (`HistoryHistoryGrid_Companion`,
  `HistoryGridSKU_Companion_HindsightingSIZEVIEWSSKUView`), but no screen
  references either of them.
- **Sibling tenants:** AER/TSN/UNS run from the same `aeo-configs` branch and
  code (`customers/AEO/config_sources.json`), but each has its own OCI
  prefix. Whether their QA/staging overlays were synced is not recorded.
- Merge into `hindsighting`, PR status and staging/prod deploy are **not
  recorded locally**. As of the local clone, `1a2ce34` exists only on
  `SUP-4610` / `origin/SUP-4610`.

## Knowledge gained (techno-functional — required)

**Technical:** a companion card above style color level gets its photo from
whatever style color the pivot returns as `top_stylecolor`. darwin's
`additionalDecorations` maps that column to the `stylecolor` level and
`attribute:img:name` resolves the photo, so the rule lives in the pivot's
`ORDER BY ... LIMIT 1 BY <level>`. AEO's `aeo_sku_temp_flow_flag.net_sls_u` is
**stylecolor-grain data repeated on every SKU row**. Summing it across SKUs
multiplies by size count. Take per-stylecolor sales from `p_history_agg`
(product = stylecolor) with the grid's filters and `* exchange_rate` instead.

**Functional:** at Department / Super Class / ERP Class the card photo is the
"face" of the group: planners read it as "this is what is driving this
group". It should be the top seller by **Net Sales $** for the selected weeks,
locations and price statuses. It should match the #1 item in Style Color
Review > Grid View and be the same on every screen that shows the group. This
follows the same rule SUP-4193 set for the style-level photo in Style Review.

## Gotchas

- **Detection tip:** for "image is not the top seller" or "image differs
  between views" tickets, find the view's `attribute:img:name`, then the
  model's `additionalDecorations.columnName`. Read the pivot's
  `ORDER BY ... LIMIT 1 BY` that fills that column, then check the grain of
  the ranking measure.
- **Never sum `aeo_sku_temp_flow_flag.net_sls_u` (or similar flow-flag
  measures) across SKUs** for a stylecolor total. A quick test: query one
  week per SKU, and identical values on every size row mean the grain is
  repeated.
- `PRODUCT.product` means **stylecolor** in `history_product_ty.ftl` pivots
  but **SKU** in `history_product_ty_sku.ftl` pivots. Join dollars on the
  right column.
- The ClickHouse version used here rejects two `JOIN ... USING` at one FROM
  level. Switch to `ON` with aliases, or nest. With `ON`, prefix any column
  that exists on both sides (e.g. `p.stylecolor` in the SKU pivot).
- Always add a deterministic tie-breaker (`, stylecolor`) after the ranking
  measure in `LIMIT 1 BY`. Otherwise ties can change the photo between loads.
- `currency_conv.location` is a **marketplace**, not a store. Bridge through
  `INV_LOCATION` (`store_hier_attr.marketplace`). A missing rate counts as 0,
  the same as in the grid.
- **The best item depends on scope.** A Grid View check on a different window
  (2025-W26 to 2026-W29) ranked items differently. Take screenshots, queries
  and test steps on one identical scope.
- **Scope check:** in git config, Cat Summary and SKU View are the only AEO
  Worklist / `levelBy` group-level photo cards. Style Review already picks
  the style's photo by `sum(net_sls_r)` (SUP-4193), but without
  `exchange_rate` or a tie-breaker. Every other image card is one style color
  showing its own photo.
- **Open with the client:** explicit confirmation that the Net Sls $ rule
  applies to every Level and should ignore the Order By dropdown is not
  recorded locally.
