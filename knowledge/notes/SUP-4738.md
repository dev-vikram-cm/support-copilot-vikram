## Problem

TB's `V_MemberBasedValidValues` table in Vertica had no version-controlled
definition or refresh mechanism — it was an out-of-band object that
`export_mod.sql` exported from as-is. This is the same table [SUP-3061](SUP-3061.md)
root-caused as loading empty every batch (because the pipeline originally
pointed at a *different*, never-created object, `V_MemberBasedValidValues_View`)
which silently broke `ccperf` ("Performance") banding on Hindsighting screens.
This ticket proactively closes the remaining drift risk: make the table a
real, git-tracked constant table like TRD/AEO already have for the same data.

## Diagnosis path

Not a bug investigation — a follow-through on SUP-3061's recommendation
(section B: "seed the ccperf band labels... TB has no constant-table
mechanism"). Confirmed before building:
- TB has no `constant_tables/` directory (unlike TRD/AEO) — it does have a
  lighter existing mechanism, `mappings/` + `02.5_load_mappings.sql`, used
  for other reference CSVs. Reused that pattern instead of introducing a new one.
- `git log --all -S "V_MemberBasedValidValues"` across `etl-tb-batch` history
  confirmed no prior `CREATE VIEW`/`CREATE TABLE` for this table anywhere —
  it really was unmanaged.
- Checked for a ClickHouse-side consumer of this table (the ticket mentions
  "further PG and CH tables") — found none in `etl-tb-batch` on TB's active
  branch (`etl_assortment_planning`). darwin reads this data straight from
  Postgres (`MemberBasedValidValuesFacade.java:36`, per SUP-3061). Only
  `etl-modern` branches on *other* tenants have a CH-side table.

## Fix

- `mappings/tb_v_memberbasedvalidvalues.csv` — new constant CSV, 17 rows
  across attribute groups `Grade`, `CCPerf`, `SlsR_Band`.
- `vertica/02.6_load_memberbasedvalidvalues.sql` — new script: truncates
  `V_MemberBasedValidValues` and `\copy`-loads it from the CSV every run,
  stamping `eventdate` with `current_timestamp`.
- `06_t.sh` — calls the new script right after the existing
  `02.5_load_mappings.sql` step, before `11_ServiceParam.sql`.
- Commit: `df0d9d3` on branch `SUP-4738` in `etl-tb-batch`
  ("Added v_memberbasedvalidvalues as constant table in vertica ETL").
- Downstream `export_mod.sql` / `pg/load.sql` were **not** touched by this
  ticket — they were already repointed at the real table and ccperf-normalized
  by the earlier SUP-3061 fix (commits `1be7df2`, `46deb35`).

## Knowledge gained (techno-functional)

**Technical:** TB's constant-reference-data pattern is `mappings/*.csv` +
a `vertica/0N_load_*.sql` truncate/`\copy` step wired into `06_t.sh` — a
lighter equivalent of TRD/AEO's `constant_tables/` + deploy process. Any
value read by config as a `dataIndex`/`groupingKey` (e.g. `grade`, `ccperf`)
must be lowercase to match; only casing that's explicitly normalized
downstream (like the existing `ccperf` UPDATE in `pg/load.sql`) is safe —
new attribute groups added to a valid-values CSV need the same treatment
if they ship mixed-case.

**Functional:** Grade, CC Performance (1–5 sales-quintile band), and SlsR
Band are planner-facing labels for grouping/filtering style-colors in
Hindsighting (Style/Stylecolor/Collection Review). Moving their source to a
version-controlled constant table makes these labels deploy-reviewable and
removes the class of silent-empty-table failure seen in SUP-3061.

## Gotchas

- **Casing gap not yet closed:** the new CSV ships `Grade` and `SlsR_Band`
  attributeids in mixed case; `pg/load.sql` only lowercase-normalizes
  `ccperf`. TB config (`tb-configs-v2` viewdefns) reads lowercase `grade`
  only — if darwin's PG query is case-sensitive, `Grade` rows won't match
  and this ticket could reproduce a milder version of SUP-3061 for the
  Grade group-by. Needs verification before prod.
- **`SlsR_Band` consumer unconfirmed:** no reference to that exact
  attributeid found anywhere in `tb-configs-v2`; the only `slsr_band` hit is
  an unrelated ClickHouse-computed quantile band (`pivot/include/inline_banding.ftl`),
  not sourced from this table. Confirm with the reporter before assuming
  these rows are used.
- **No ClickHouse table exists for this on TB** — if the ticket's "CH
  tables" language was copied from a different tenant's similar ticket,
  that part doesn't apply here.
